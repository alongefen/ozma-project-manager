# מסד P1.2

פיתוח ובדיקות בענן בלבד, בפרויקט `izjmvyguzbampoasvnru`. אין Docker או מסד מקומי.

המיגרציה הראשונה יוצרת 17 טבלאות ב-public, סכמה פרטית לפונקציות הרשאה, אילוצים, אינדקסים, טריגרים ופונקציות RPC. היא אינה מוסיפה משתמש, דלי אחסון או הגדרות Auth. האחרונים בבעלות P1.3. שמות הדליים בחוזה: `originals`, `display`; שניהם פרטיים.

## הפעלה ודרך חזרה

- P1.1 מוזגה ב-`b17c5fb2d5421aa7ae01d31fac30196830948b76`, ובוצע rebase.
- A-27 מאשרת את המיגרציה הראשונה. אלון אישר בשיחת P1.2 ב-22.11.2026 את הפרויקט הקיים באירלנד, למרות תנאי פרנקפורט המקורי.
- אימות החיבור: ארגון `ozma`, תוכנית Free, פרויקט פעיל, כ-11MB; אין אובייקטים או פונקציות ב-public/private, אין דליים, משתמשי Auth או מיגרציות קודמות.
- SQL ו-PL/pgSQL נבדקים במנתח תחביר לפני ההפעלה (טיפוסי קטלוג מוחלפים זמנית במנתח בלבד). זו אינה הוכחה לתקינות הרשאות; הבדיקות מול API נדרשות אחרי ההפעלה.
- כל המיגרציה בטרנזקציה: כשל מחזיר את המסד למצב הקודם. אין מחיקת אובייקט קיים או העתקת נתוני לקוח.
- אחרי הצלחה: אין rollback הרסני אוטומטי. אם נדרש תיקון, מכינים מיגרציית המשך לסקירה ולא מאפסים את המסד. הסרת סכמה לאחר שימוש דורשת אישור נפרד.

## בדיקות

`npm run test:db` מריץ סדרתית. נדרשים `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` בסביבה או ב-`.env.local` המוחרג מ-Git. אין להציג את ערכיהם.
הבדיקות משתמשות בשמות ומזהים בדויים ייחודיים ומשאירות את הנתונים לצורך ההיסטוריה; אין איפוס או מחיקה של משתמשים.

הפונקציות הציבוריות מקבלות `{input: ...}` ב-camelCase. שגיאות RPC מכילות את קוד החוזה ב-message; P1.3 ממירה אותו ל-AppError והודעה בעברית. סיסמאות אינן נשלחות ל-RPC.
`begin_upload` מחזירה תיאור קובץ בלבד, ללא אסימון. P1.3 חותמת על ההעלאה.
`system_finish_upload` מקבלת actorId ו-sessionId שנגזרו מהסשן המאומת בשרת, ותוכן שנבדק בשרת; היא בודקת מחדש סשן, שיוך, מצב פרויקט והקובץ.

המיגרציות המוחלות בענן: `20261122143622`, `20261122144510`, `20261122145408`, `20261122153222`. השנייה והשלישית מתקנות התנגשות שם באימות קלט ומזהה ישות בלוג. שתיהן הופעלו באישור אלון; אין שינוי היסטוריה קיימת.

## חוזי ניסיון חוזר — P1.2-FOLLOWUP

המיגרציה `20261122153222_retry_profile_and_upload_completion.sql` הוכנה ונסקרה. אלון אישר במפורש את הפעלתה ב-22.11.2026 במסגרת D31, בפרויקט הקיים בלבד; המיגרציה הופעלה בהצלחה בחלון מתואם עם P1.3 ונרשמה בענן כ-`20261122153222`. שם הקובץ המקומי הותאם לגרסה בענן ללא שינוי SQL, למניעת הפעלה חוזרת. האישור אינו חל על מיגרציה נוספת.

- `AuthAdmin.createUser` ו-`UsersApi.createUser` דורשות `requestId`, ‏`email`, ‏`fullName`, ‏`password`. שומרים את אותו requestId ואותו קלט בניסיון חוזר; בקשת יצירה חדשה מקבלת מזהה חדש.
- `create_profile({requestId,email,fullName})` מחזירה `Saved` עם `passwordPending`. הבעלים והקלט נשמרים בקבלה פרטית באותה טרנזקציה עם הפרופיל. חשבון ישן בלי קבלה, בקשה חדשה לאותו חשבון או שימוש בבקשה עם אימייל/שם אחר נדחים. הפרופיל אינו הוכחה שהסיסמה הושלמה.
- צרכן P1.3: מאמת בעלים, יוצר Auth או מאתר משתמש Auth קיים, ואז קורא `create_profile`. רק כשהתוצאה `passwordPending:true` מותר להשלים את סיסמת בקשת היצירה. לאחר הצלחת Auth קוראים `complete_profile_creation({requestId,userId})`; פונקציה זו מבטלת סשנים מוקדמים ומסמנת השלמה אטומית. אין לקרוא `revoke_user_sessions` בנפרד במסלול יצירה זה. אם Auth נכשל, הקבלה נשארת pending וניתן לנסות שוב; אם תשובת השלמת המסד אבדה, החזרה מחזירה `passwordPending:false` ואסור לשנות סיסמה שוב. איפוס רגיל נשאר פעולה נפרדת.
- סיסמה או fingerprint שלה אינם נשלחים למסד. שמירת אותה סיסמה בניסיון חוזר בזמן pending היא באחריות orchestration ב-P1.3; המסד מסמיך רק בעלים פעיל להמשיך את בקשתו. מסד לבדו אינו מוכיח ש-Auth הצליח: רק שירות השרת קורא completion לאחר הצלחת Auth. משתמש Auth חדש שכבר נוצר עם הסיסמה הנכונה יכול לעבור ישירות ל-completion אחרי create_profile.
- `get_pending_upload` מחזירה `state` ו-`fileRef` (רק ב-ready), לצד תיאור ההעלאה הקודם. השם נשמר לתאימות. ב-ready הצרכן מחזיר את התוצאה בלי להוריד או ליצור preview שוב; ב-rejected הוא מחזיר כשל אימות. `system_finish_upload` מאפשרת חזרה עם תוצאה זהה בלבד, אחרי בדיקת מעלה, סשן והרשאות חיות, ובלי עדכון השורה שכבר הושלמה.
- שחזור terminal מותר רק כל עוד הקובץ לא נקשר למסמך, לשער או לצירוף דיווח. אחרי קישור, משתמשים במסלול הקריאה הרגיל; finish אינו מקנה זכות קריאה למעלה שנשללה ממנו גישה. גוף/מצב סותרים נדחים ב-CONFLICT.

הטיפוסים ב-`src/types/database.ts` הופקו מהענן לאחר ההפעלה; חתימת RPC החדש זהה לחתימה שהוכנה ונסקרה. אין כאן שינוי API ציבורי בספק או שינוי סיסמאות קיים.

## עדכון שם ואימייל — P1.3-PROFILE-UPDATE 

המיגרציה `20261122175041_atomic_profile_email_update.sql` הופעלה בפרויקט הפיתוח באישור D31 (23.11.2026). בלי המיגרציה `setEmail` מחזירה UNAVAILABLE ואינה משנה את Auth.

סדר הקריאות בשרת, אחרי בדיקת בעלים:

1. `prepare_profile_update({id,expectedRevision,fullName,email})` מחזירה `{id,revision,emailPending}`. עריכה ישנה ואימייל תפוס נדחים כאן, לפני Auth.
2. אם `emailPending:false`, השמירה הושלמה ואין קריאה ל-Auth. כך גם בשינוי שם בלבד ובחזרה על בקשה שכבר הושלמה.
3. אם `emailPending:true`, משנים אימייל ב-Auth בתוך דקה. טריגר על `auth.users` שומר שם, אימייל, גרסה ואירוע באותה טרנזקציה. אם אין הכנה תקפה, הגרסה השתנתה או סשן המבצע בוטל, גם השינוי ב-Auth מתבטל.
4. תמיד קוראים את גרסת הפרופיל אחרי Auth, גם אם התשובה אבדה. אם הגרסה לא השתנתה, השמירה טרם בוצעה ומחזירים שגיאה. בקשת Auth שתשובתה אבדה עוד יכולה להישמר בתוך הדקה, וניסיון חוזר עם אותו קלט מחזיר אז את הקבלה.
5. אם הגרסה השתנתה, קוראים שוב ל-`prepare_profile_update` עם אותו קלט. הקריאה אינה יכולה לכתוב: היא מחזירה את הקבלה (הצלחה, `emailPending:false`) או CONFLICT. שם ואימייל זהים בפרופיל אינם הוכחה ש-Auth השתנה. אין קוראים ל-Auth שוב.

ניסיון חוזר נעשה עם אותו קלט ואותה גרסה. אין לקרוא `update_profile` אחרי Auth ואין לבצע פיצוי.

אחרי ההפעלה, שינוי אימייל ישיר ב-Auth לחשבון שיש לו פרופיל נדחה, גם מלוח הבקרה, וכך גם מחיקה רכה שמשנה את האימייל. שינוי סיסמה וחשבון בלי פרופיל אינם מושפעים.

דרך חזרה, רק במיגרציית המשך ובאישור, ובשני שלבים נפרדים. הסרה ישירה של הטריגר פותחת חלון שבו Auth משתנה בלי הפרופיל, ומפתחת מחדש את הבאג:

1. טרנזקציה ראשונה, עם commit: `revoke execute on function public.prepare_profile_update(jsonb) from authenticated;`. כך לא נוצרת כוונה חדשה.
2. המתנה של יותר מ-70 שניות, כדי שכל כוונה קיימת תפוג (תוקף דקה) ובקשת Auth בדרך תידחה או תסתיים.
3. רק אז, בטרנזקציה שנייה: `drop trigger apply_profile_email on auth.users;`. הטבלה והקבלות נשארות.

בלי הטריגר אין להשתמש בשינוי אימייל, כי Auth והפרופיל אינם נשמרים יחד.
